# DEVIATIONS.md - Event Management System (Team 13)

Owner: Product Owner. Lists the differences between the submitted documents (SRS v1.0 05-09-2026, SAD v1.0 14-09-2026, Test Plan v1.0 14-09-2026) and the final build, where the SRS could not be followed as written. Each entry has a reason why. Last updated 13-11-2026.

Status key: **Resolved** = decision recorded, **Open** = needs a follow-up outside the code.

| ID   | Area | What the SRS says | What was built instead | Why the SRS could not be followed | Status |
|------|------|-------------------|------------------------|-----------------------------------|--------|
| D-01 | Response time target (NF-001) | SRS 5, SAD 3.1 and the Test Plan say **<= 3 s for 90%** of requests. The SRS RTM says **< 2 s for 95%**. | Built and tested against **3 s / 90%** (TC-Perf-01). | The SRS contradicts itself. 3 of 4 places agree on 3 s / 90%, so that is the acceptance criterion. The RTM row is to be corrected. | Resolved |
| D-02 | Email and SMS notifications (F-018) | Attendees are alerted when an event is cancelled. | Alerts are stored as **in-app notifications** for every attendee who booked. Email is sent only when a provider webhook is configured (3 retries). SMS is not built. | No email or SMS provider account exists (SAD 6 "finalize notification provider"), and a student project cannot pay for one. In-app alerts still reach everyone who booked. | Resolved |
| D-03 | Payment gateway (F-013) | Payments go through a payment gateway. | A pluggable gateway: **Razorpay test mode** when keys are set, otherwise a built-in **sandbox** that signs payments the same way. | A live merchant account needs business registration, which a college project does not have. Tests and demos must also run offline. | Resolved |
| D-04 | Receipt format (F-014) | A receipt is shown right after payment. | An on-screen receipt page with **Print / save as PDF**. It is not a generated PDF file or an email attachment. | The email copy depends on the notification provider (D-02). The browser print function meets "shown right after paying" without extra libraries. | Resolved |
| D-05 | Performance test tool and environment (NF-001, Test Plan 5) | JMeter on a production-like environment. | `npm run perf` (Node script) on a developer laptop with local MongoDB. Results are in `docs/PERFORMANCE.md`. | No staging or production server exists, so a production-like run is not possible. The script hits the same endpoints JMeter would. | Open (repeat when deployed) |
| D-06 | Uptime (NF-002) | 99.5% monthly uptime, shown in Ops reports. | `GET /api/health` and `/api/health/metrics` are provided for an uptime monitor. No uptime figure is reported. | Uptime needs a deployed system running for a month. A course project has no hosting. | Open |
| D-07 | Encryption at rest (RTM wording of NF-003) | RTM says "encrypt at rest and in transit". | TLS is enforced, passwords are bcrypt-hashed and no card data is stored. No application-level encryption of other fields. | Encryption at rest is provided by the database host (for example MongoDB Atlas), which is chosen at deployment. SRS 5 only requires HTTPS and no plaintext passwords, and that is met. | Open (decide at deployment) |
| D-08 | TLS verification (SR-001, TC-Sec-01) | TLS 1.2+ verified, including a traffic scan of the deployed system. | TLS is enforced in code (`minVersion TLSv1.2`, HSTS). One TLS server test is **skipped** and the traffic scan is not done. `npm run check:tls` and `docs/TLS.md` explain how to run them. | There is no deployed server, and OpenSSL was not available on the Windows test machine. | Open |
| D-09 | 2-year log retention test (NF-004, TC-OPS-01) | Logs are kept for at least 2 years, with archival and retrieval verified. | Each log row stores `retainUntil` (>= 730 days) and is removed only by MongoDB's TTL index. Tests check the stored date, using in-memory collections. | A 2-year wait cannot be tested or demoed, so the stored date is checked instead. | Resolved |
| D-10 | Delete events and user management (SRS 2.2) | SRS 2.2 lists "delete events", "manage participants" and "administrative management of users". | Built: cancel event (F-006) and edit event (F-005). No delete endpoint and no user management screen. | SRS section 4 and the RTM have no requirement for these, so they are not testable. Cancelling keeps bookings and refunds consistent, which deletion would break. | Resolved |
